# UUIDv7 Crate Selection

- **Status:** Research findings + recommendation
- **Decision context:** record identifiers are UUIDv7, generated by an existing crate (no hand-rolled UUIDv7), for monotonic sort-by-time ordering. Storage is SQLite via `rusqlite` with SQLCipher; identifiers are stored as **string primary keys (TEXT)**, per the shared schema conventions in [Master Appendix A §3](../specs/master/appendix-a-sync-ready-schema-and-municipal-integration.md) ("`id` — a UUIDv4 (or ULID) string primary key"), which a prior charting decision upgraded from UUIDv4 → UUIDv7. The string/TEXT shape is the expected representation.
- **Research date:** 2026 (verified against primary sources below).

> **Source-policy note.** Every fact in this document was verified against a primary source: the crates.io registry index (cloned / fetched from `rust-lang/crates.io-index`, the canonical mirror), the crate's own `Cargo.toml` / source, or the crate's GitHub repository (`uuid-rs/uuid`, `LiosK/uuid7-rs`, `jedisct1/rust-uuidv7`). No secondary blog write-ups were relied upon for any claim. All crates.io facts below trace to the index metadata (version, `pubtime`, `features`, `rust_version`, `yanked` flags).

## Recommendation

**Adopt the `uuid` crate, version `1.24.x` (`1.24.1` as of this writing), with the `v7` + `serde` features enabled.**

```toml
[dependencies]
uuid = { version = "1", features = ["v7", "serde"] }
```

- Version `1.24.1` is the current release on crates.io: published `2026-08-14T23:37:51Z`, `yanked: false`, MSRV `rust-version = "1.85.0"`.
  ([crates.io-index `uuid` entry](https://github.com/rust-lang/crates.io-index/blob/master/uu/id/uuid))
- The matching GitHub release is tag `v1.24.1`, published `2026-08-14T23:36:35Z`; the repo (`uuid-rs/uuid`, 1.2k+ stars) was last pushed `2026-08-14T23:36:38Z` — i.e. it is actively maintained.
  ([`uuid-rs/uuid` repo](https://github.com/uuid-rs/uuid), [releases/latest](https://github.com/uuid-rs/uuid/releases/tag/v1.24.1))

### One-line rationale

The `uuid` crate is the de-facto standard, actively-maintained UUID library for Rust; its `v7` feature implements RFC 9562 §5.7 monotonic UUIDv7 with a 42-bit dedicated counter (RFC 9562 §6.2 "Method 1"), ships first-class `serde` (human-readable string / binary bytes) support, is already transitively present in the Tauri + `rusqlite` dependency graph, and slots directly into TEXT-key storage via `Uuid::to_string()`.

## The `uuid` crate (recommended)

- **Package / repo:** `uuid` 1.24.1 — https://crates.io/crates/uuid, https://docs.rs/uuid, source https://github.com/uuid-rs/uuid.
- **(a) Maintenance.** Current version `1.24.1` (`2026-08-14`). Repo `uuid-rs/uuid`: 1,232 stars, pushed `2026-08-14T23:36:38Z` (same minute as the release). License Apache-2.0 OR MIT. Crate badge: `maintenance = "actively-developed"`.
  ([crates.io-index `uuid`](https://github.com/rust-lang/crates.io-index/blob/master/uu/id/uuid); [`uuid-rs/uuid`](https://github.com/uuid-rs/uuid))
- **(b) Monotonic UUIDv7.** `Uuid::now_v7()` is guaranteed monotonic *per process*: the doc comment states "All UUIDs generated through this method by the same process are guaranteed to be ordered by their creation." It forwards to `Uuid::new_v7(Timestamp::now(shared_context_v7()))`, where `shared_context_v7()` is a `static LazyLock`-like `Mutex<ContextV7>` — a **process-wide shared counter**.
  - **Mechanism (RFC 9562 §6.2, Method 1 — fixed-length dedicated counter bits):** `ContextV7` implements `ClockSequence` with `USABLE_BITS = 42`. Its `generate_timestamp_sequence`:
    1. reseeds the counter to a **random 41-bit value** each time the millisecond advances (`Counter::reseed` → `rng::u64() & RESEED_MASK`, where `RESEED_MASK = u64::MAX >> 23` keeps the 42nd bit unset so the counter can increment safely);
    2. **increments** the counter within the same millisecond (`Counter::increment`, `value += 1`);
    3. on the (astronomically unlikely) 42-bit overflow, **increments the timestamp by 1 ms and reseeds** — preserving monotonicity at the cost of a forward-shifted `unix_ts_ms`.
  - `Uuid::new_v7` then merges the 42-bit counter into the `rand_a` (12 bits) + `rand_b` (62 bits, split around the 2-bit variant field) region, filling the remaining bits with random data; the 48-bit `unix_ts_ms` (milliseconds) occupies the leading bits so UUID byte/string order matches time order.
  - Source of truth: `src/v7.rs` (`Uuid::now_v7`, `Uuid::new_v7`) and `src/timestamp.rs` `context::v7_support` (`ContextV7`, `Counter::reseed/increment`, `RESEED_MASK`, `USABLE_BITS = 42`) in the `uuid` crate.
- **(b, cont.) `Timestamp` field exposure.** `Timestamp::to_unix(&self) -> (u64, u32)` exposes the `(seconds, subsec_nanos)`; but the **counter is deliberately NOT exposed publicly** — `Timestamp::counter()` is `pub(crate)`, with the source note: "the usable counter bits are lost in a version 7 UUID so can't be reliably recovered." The `unix_ts_ms` of a v7 UUID is *recoverable* via `Uuid::get_timestamp()` (returns `Option<Timestamp>`; supported for v1/v6/v7). So the clean `(unix_ts_ms, counter)` tuple is **not** a public API surface; you get the timestamp (decoded) and the UUID value, not the raw counter. This matters if a charting/telemetry consumer expected to read counters directly — they cannot through `uuid` (and neither can they through `uuid7`).
  ([`uuid` `src/timestamp.rs`](https://github.com/uuid-rs/uuid/blob/main/src/timestamp.rs) — `counter()` `pub(crate)`, `to_unix()` `pub const`; `src/v7.rs` — `new_v7`, `now_v7`)
- **(c) Ergonomics for Tauri + SQLCipher.**
  - **serde:** `serde = ["dep:serde_core"]` (depends on `serde_core`, so `no_std`-friendly). `Serialize for Uuid` emits `serialize_str(self.hyphenated())` when the serializer is **human-readable** (JSON, TOML, a `String`-oriented format) and `serialize_bytes(self.as_bytes())` (16 raw bytes) otherwise. `Deserialize` is symmetric. `uuid::serde::compact`, `simple`, `hyphenated`, `braced`, `urn` helpers allow forcing a specific representation. → For a TEXT PK you serialize the hyphenated string; for a BLOB you use the binary path.
    (Source: `src/external/serde_support.rs`)
  - **rusqlite interop:** `rusqlite` (feature `uuid`) implements `ToSql`/`FromSql` for `uuid::Uuid`, but it stores/reads **`Value::Blob`** — `From<uuid::Uuid> for Value` = `Self::Blob(id.as_bytes().to_vec())`, and `FromSql` reads a `[u8; 16]` then `Uuid::from_u128(u128::from_be_bytes(bytes))`. **Consequence for this repo:** do **not** enable rusqlite's `uuid` feature to persist IDs — it would write BLOBs, violating the TEXT-string-PK convention. Instead store `Uuid::to_string()` (or `.as_simple().to_string()`) into a `String` parameter.
    (Source: `rusqlite` `src/types/value.rs`, `src/types/to_sql.rs`, `src/types/from_sql.rs`; `Cargo.toml` `uuid = "1.0"` gated on `#[cfg(feature = "uuid")]`)
  - **Feature flags (relevant):** `default = ["std"]`; `v7 = ["rng"]` (non-default); `rng = ["dep:getrandom"]`; `fast-rng = ["rng", "dep:rand"]` (uses `rand 0.10` instead of `getrandom`); `serde` (non-default); plus `v1`…`v8`. There is **no** macro/const for v7 (only v1…v5 have const `Uuid::from_uuid_bytes`/`from_fields` equivalents; v7 requires `v7` feature and runtime RNG).
    (Source: `uuid` `Cargo.toml` / index `features2`)
  - **Randomness source (the "unreliable `std::fs` fallback" concern):** `uuid`'s `rng` feature does **not** read `/dev/urandom` via `std::fs`. It calls `getrandom::fill`, which goes to the OS/CPU RNG (Windows `BCryptGenRandom`, Linux `getrandom(2)`, etc.), and panics if that fails. The `fast-rng` / `rng-rand` path uses `rand` (`rand::random`). On `wasm32-unknown-unknown` it requires one of `js` / `rng-getrandom` / `rng-rand` (compile_error otherwise). So there is no fragile user-space `/dev/urandom` `std::fs::File` fallback in this crate. (If a *caller* hand-rolled a `ClockSequence`/seeder, that would be on them.)
    (Source: `uuid` `src/rng.rs`)
  - **MSRV / std / no_std:** `rust-version = "1.85.0"` (raised from `1.63.0` in the 1.20→1.23 window). The crate supports `no_std` (`default = ["std"]`; without `std` you drop `now_v7()` — note `Uuid::now_v7()` is gated `#[cfg(feature = "std")]` — and must provide your own time/counter via `Timestamp::now(context)`/`Timestamp::from_unix_time`). `atomic` feature (for v1/v6) uses the `atomic` crate, not `alloc`.
  - **SqlitePool / concurrency:** `now_v7()` uses a single process-wide `Mutex<ContextV7>`, so cross-thread monotonicity holds within a process; there is **no cross-process guarantee** (each process reseeds independently). For a single-process Tauri app writing through one `rusqlite` `Connection` (SQLCipher), this is exactly the guarantee needed. `fast-rng` (a thread-local `rand` RNG) is the only RNG-related alternative and does not change the counter semantics.
- **(d) Real published crate.** Yes — crates.io `uuid` 1.24.1, `yanked: false`, checksum `2cefc03fd367c0c6d4305de1b312cf00248c4114f4a0418ce6a6af769e3b0bd9`.

**Why it wins here.** It is the only candidate with (1) first-class serde (string/binary), (2) an RFC 9562-compliant monotonic v7 with a 42-bit counter and overflow-handling timestamp increment, (3) active maintenance and a 1.2k-star community, (4) already-in-graph compatibility with `rusqlite` (even though we deliberately *avoid* rusqlite's BLOB `uuid` feature), and (5) no `std::fs` randomness fragility (uses `getrandom`).

## Alternatives considered

### `uuid7` (crate `uuid7`; repo `LiosK/uuid7-rs`) — strongest runner-up

> The user's prompt wrote "`uuidv7`" but the notable, actively-maintained crate of that family is **`uuid7`** (LiosK) — the author of the widely-referenced draft `uuidv7` algorithm spec. This is the crate to weigh against `uuid`, not the tiny `uuidv7` crate (below).

- **Package / repo / version.** `uuid7` **1.8.0**, crates.io `pubtime` `2026-05-17T22:02:18Z`, `yanked: false`, `rust-version = "1.85"`, edition 2024. Repo `LiosK/uuid7-rs`, pushed `2026-05-17T22:02:25Z`, 36 stars. License Apache-2.0.
  ([crates.io-index `uuid7`](https://github.com/rust-lang/crates.io-index/blob/master/uu/id/uuid7); [`LiosK/uuid7-rs`](https://github.com/LiosK/uuid7-rs))
- **(b) Monotonicity.** Same RFC 9562 Method 1 design as `uuid`: `V7Generator::generate_or_abort_with_ts` uses `MAX_COUNTER = (1 << 42) - 1`; on a new millisecond it reseeds `counter = rand.next_u64() & MAX_COUNTER` (42-bit), within a millisecond it does `counter += 1`, and on 42-bit overflow it increments `timestamp_biased` (the millisecond) and reseeds. `uuid7()` is backed by a process-wide `LazyLock<Mutex<GlobalGenInner>>` generator, with `forkguard` to reset on fork (Unix). Clock rollback within 10 s (`rollback_allowance = 10_000` ms) is absorbed by reusing the previous timestamp; larger rollback resets the generator (breaks monotonicity by design).
  (Sources: `uuid7` `src/generator.rs` `generate_or_abort_with_ts`; `src/global_gen.rs`; README "Field and bit layout")
- **(c) Ergonomics.** `serde` is a **non-default** feature (serializes `Uuid`); `default = ["global_gen"]`, `global_gen = ["std", dep:forkguard, dep:reseeding_rng]`; optional `rand010`/`rand09`/`rand08` adapters; optional `uuid` feature (with `global_gen`) enables `new_v7() -> uuid::Uuid` bridging to the `uuid` crate. `no_std` supported (`#![cfg_attr(not(feature = "std"), no_std)]`); without `std` you provide your own `TimeSource`. It provides a **standalone 16-byte `Uuid` type** (its own `id::Uuid`, not the `uuid` crate type) with `to_string()` / `as_bytes()` / `from_str`.
  - **Interop caveat:** its `Uuid` is a distinct type from `uuid::Uuid`. `rusqlite`'s `uuid` feature (ToSql/FromSql) is implemented for the *`uuid` crate's* `Uuid`, **not** `uuid7::Uuid` — so you'd store via `Uuid::to_string() -> String` manually, or enable the bridge `uuid` + `global_gen` features and call `uuid7::new_v7()` to get a real `uuid::Uuid`. There is no serde `as str` vs `as bytes` toggle documented beyond the default string representation.
  - MSRV `1.85`, edition 2024 (same MSRV as `uuid`).
- **Trade-offs vs `uuid`.** Clean, focused, spec-faithful v7 design with an excellent README and fork safety. But it is a **major-version-1, ~36-star, single-maintainer** crate whose `Uuid` type is not the ecosystem standard, and it does **not** integrate with `rusqlite`/`sqlx` out of the box the way `uuid::Uuid` does. Adopting it would add a second UUID type to the codebase (or force a bridge dependency) for no functional gain over `uuid`'s `v7`. Prefer `uuid` for ecosystem depth; `uuid7` is the fallback if we ever want a minimal, fork-safe, focused v7 generator.

## Rationale (tied to BMS requirements)

1. **Monotonic sort-by-time.** BMS records must sort chronologically by identifier. `uuid`'s `v7` (`Uuid::now_v7()`) lays the 48-bit `unix_ts_ms` in the leading bytes and fills `rand_a`+`rand_b` with a 42-bit counter + random bits, so **byte-wise and string-wise ordering equals creation order** (within a process). Verified at `src/v7.rs` + `src/timestamp.rs` (`ContextV7`, 42-bit reseeding counter, overflow→timestamp increment). The `test_sorting` test asserts `uuid1.as_bytes() < uuid2.as_bytes()` and `uuid1.to_string() < uuid2.to_string()` for in-order timestamps; the `context` test asserts in-millisecond counter monotonicity.
2. **TEXT primary keys.** The repo stores `id` as a string PK (Master Appendix A §3). `uuid`'s serde `Serialize`/`Deserialize` human-readable mode is a hyphenated string (`Uuid::to_string()` / `parse_str`), which is exactly the TEXT shape. We deliberately **avoid** rusqlite's `uuid` feature because it BLOBs the value (verified in `rusqlite` source); instead we bind a `String`.
3. **rusqlite / serde interop.** Guaranteed `serde` support via a non-default but trivial feature; `rusqlite`'s `uuid` interop exists (BLOB) but we use the string path. `sqlx` (not currently in this repo's stack) likewise has battletested `Uuid` `Encode`/`Decode` + `Type` impls via its `uuid` feature — so the `uuid` crate is the future-proof choice if sqlx ever enters the stack.
4. **Existing and maintained.** `uuid` 1.24.1 is current and actively developed (release + push on 2026-08-14), 1.2k stars, and already transitively present across the Tauri/`rusqlite` ecosystem, minimizing new dependency surface. Runners-up `uuid7` (focused but minority) and `uuidv7` (dormant 0.1.x) trade away ecosystem maturity for no compensating BMS benefit.

### Known caveats to carry into the TDD

- `now_v7()` is **`std`-only** (gated `#[cfg(feature = "std")]`) and requires the `v7` (→ `rng` → `getrandom`) feature. `fast-rng` swaps `getrandom` for `rand` if preferred.
- Monotonicity is **per-process** (shared `Mutex<ContextV7>`); there is **no cross-process / cross-restart monotonicity** and no cross-device ordering beyond what `unix_ts_ms` provides. Single-writer SQLCipher use is therefore the supported shape — consistent with the repo's "single logical write path" (Core-Engine NFR-05).
- The raw **counter is not readable** from a generated `Uuid` (`Timestamp::counter()` is `pub(crate)`); only the timestamp is recoverable (`Uuid::get_timestamp()`).
- No `const`/macro v7 constructor (needs runtime RNG + clock). Use `Uuid::now_v7()` at insert time.
- Clock rollback: `uuid`'s `ContextV7` **ignores** a backwards clock by reusing the previous millisecond and incrementing the counter (monotonicity preserved, wall-clock fidelity sacrificed) — it does *not* have `uuid7`'s 10-second "significant rollback → reset" threshold. For a barangay desktop app this is the desirable behavior (IDs stay sortable even if the OS clock is corrected backward).

## Usage sketch

`Cargo.toml`:

```toml
[dependencies]
uuid = { version = "1", features = ["v7", "serde"] }
# rusqlite WITHOUT its `uuid` feature — persist IDs as TEXT strings:
rusqlite = { version = "0.40", features = ["bundled-sqlcipher", "bundled", "fts5"] }
#                                    ^ note: 'bundled-sqlcipher' feature name may differ;
#                                    confirm against rusqlite docs at the time of implementation
```

Generate → serialize to TEXT → parse back → order check:

```rust
use uuid::Uuid;

// 1. Generate a monotonic (within this process) UUIDv7.
let id: Uuid = Uuid::now_v7();                   // requires `v7` + `std` (default) features

// 2. Serialize to a TEXT string for the SQLCipher STRING primary key.
//    Hyphenated lowercase canonical form: "018f..." — this is what serde's
//    human-readable serializer emits, and what `to_string()` produces.
let id_text: String = id.to_string();

// 3. (rusqlite) Bind as a String TEXT value, NOT via rusqlite's `uuid` feature
//    (that feature stores a 16-byte BLOB). Example:
//    conn.execute(
//        "INSERT INTO residents (id, barangay_code, ...) VALUES (?1, ?2, ...)",
//        rusqlite::params![id_text, barangay_code],
//    )?;

// 4. Parse it back out unchanged.
let parsed: Uuid = Uuid::parse_str(&id_text).expect("valid UUIDv7 string");
assert_eq!(id, parsed);
assert_eq!(parsed.get_version(), Some(uuid::Version::SortRand)); // v7

// 5. Ordering guarantee: within one process, successive now_v7() calls sort.
let a = Uuid::now_v7();
let b = Uuid::now_v7();
assert!(a.as_bytes() < b.as_bytes()); // byte order == time order
assert!(a.to_string() < b.to_string()); // TEXT order == time order

// (optional) serde round-trip — human-readable = hyphenated string:
let json = serde_json::to_string(&id).unwrap(); // "\"018f ...\""
let round: Uuid = serde_json::from_str(&json).unwrap();
assert_eq!(id, round);
```

Feature/type-path notes, verified against current docs:

- `uuid::Uuid::now_v7()` — `src/v7.rs`, gated `#[cfg(feature = "std")]` and documented "All UUIDs generated through this method by the same process are guaranteed to be ordered by their creation."
- `uuid::Version::SortRand` is the enum discriminant for v7/v8 (`get_version()` returns `Some(Version::SortRand)` for v7).
- `uuid::serde::compact` gives `[u8; 16]`/BLOB serialization if a future schema ever switches back to BLOB — not needed for the current TEXT convention.
